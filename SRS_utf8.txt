1. Introduction
1.1 Purpose
This Software Requirements Specification (SRS) document formally defines the complete functional and non-functional requirements of the Drone Mission Planner application ΓÇö a production-grade Ground Control Station (GCS) frontend built with the Flutter framework. It is intended for use by developers, systems architects, academic evaluators, project reviewers, and all stakeholders involved in designing, implementing, testing, or extending the system. This document serves as the contractual baseline against which the system will be verified and validated.
Version 3.0 represents the finalised, production-ready specification, extending v2.0 with all remaining critical UI capabilities: manual flight control, camera and gimbal management, flight mode visualisation, mission replay, airspace awareness, advanced power analytics, system state machine, extensibility framework, and multi-vehicle management. The document additionally provides a comprehensive UI Architecture section and enhanced non-functional requirements aligned with enterprise deployment standards.
1.2 Scope
The Drone Mission Planner is a cross-platform mobile and desktop application built with the Flutter framework. The full-scope GCS UI enables drone operators and technicians to:
Plan, visualise, simulate, and manage UAV flight missions on an interactive map
Control drone hardware manually and autonomously via a unified command interface
Monitor real-time telemetry, attitude, and GNSS data through structured dashboards
Configure vehicle parameters, calibrate sensors, manage firmware, and tune PID controllers
Operate camera payloads and gimbal systems from an integrated media control panel
Replay historical flight logs with synchronised telemetry and map position
Monitor airspace restrictions, no-fly zones, and regulatory boundaries
Analyse battery and power consumption with predictive return-to-home calculations
Track and transition between drone operational states through a defined state machine
Manage multiple vehicles simultaneously from a unified multi-vehicle interface
Extend system capabilities through a modular plugin framework
This SRS covers only the frontend application. Backend services, live drone hardware communication beyond the MAVLink abstraction layer, cloud data synchronisation, and hardware-in-the-loop (HIL) simulation infrastructure are outside the scope of this document.

2. Overall Description
2.1 Product Perspective
The Drone Mission Planner is a standalone frontend application that does not depend on any external server in its current form. All data ΓÇö missions, settings, simulated telemetry, PID profiles, and flight logs ΓÇö is managed on-device. The application is architecturally positioned to integrate with a future REST/WebSocket backend and a MAVLink-based drone communication layer with minimal changes to the Domain and Presentation layers.
The v3.0 specification introduces the full operational workflow of a production GCS: operators can take manual flight control at any moment, manage camera payloads, monitor live and replayed telemetry, observe airspace constraints, and track system state through a formal FSM. The architecture is extended with a plugin framework that allows third-party module integration without core application modification.

2.4 Assumptions and Constraints
No backend server is implemented in the current version; all persistence is local (Hive/SharedPreferences).
All telemetry and camera data are simulated unless a MAVLink connection is established.
Manual control UI operates in simulated mode for safety; real actuation requires MAVLink integration.
Airspace overlay data is sourced from a third-party provider (e.g., OpenAIP or AirMap SDK) requiring internet access; the UI degrades gracefully when offline.
PID tuning, sensor calibration, and firmware flashing UIs are functional mockups in the current version; hardware actuation is deferred to the MAVLink integration phase.
The plugin framework exposes a Dart interface; actual plugin binaries require separate compilation and side-loading approval per platform.

3.21  Manual Flight Control Interface [FR-21]
ADDED v3.0 ΓÇö This section introduces the on-screen manual control UI for direct drone command input.
FR-21-01 [ADDED v3.0] The system shall provide a Manual Control screen accessible from the main navigation drawer and via a quick-access button on the map screen HUD.
FR-21-02 [ADDED v3.0] The system shall display two virtual joystick widgets on the Manual Control screen: a left joystick controlling throttle (vertical axis) and yaw (horizontal axis), and a right joystick controlling pitch (vertical axis) and roll (horizontal axis), conforming to the Mode 2 RC transmitter layout by default.
FR-21-03 [ADDED v3.0] The system shall allow the user to switch the joystick layout between Mode 1, Mode 2, Mode 3, and Mode 4 in Settings, redefining axis-to-channel assignments accordingly.
FR-21-04 [ADDED v3.0] The system shall render each virtual joystick with a circular boundary indicator, a draggable thumb that returns to centre on release (spring-return behaviour), and a crosshair overlay.
FR-21-05 [ADDED v3.0] The system shall display real-time channel output values (0ΓÇô100% or ┬▒100%) adjacent to each joystick axis as numerical readouts, updating at a minimum of 20 Hz.
FR-21-06 [ADDED v3.0] The system shall support input from a connected USB or Bluetooth HID gamepad/joystick device, mapping physical axes and buttons to the drone channel outputs per a configurable axis-mapping panel.
FR-21-07 [ADDED v3.0] The system shall support keyboard input for manual control when running on desktop platforms, with configurable key bindings for throttle, yaw, pitch, and roll increments.
FR-21-08 [ADDED v3.0] The system shall provide a Manual Override button on the mission execution HUD that, when activated, immediately suspends the autonomous mission sequence and transfers authority to the manual control input channels.
FR-21-09 [ADDED v3.0] The system shall display a prominent 'MANUAL OVERRIDE ACTIVE' banner and change the HUD border colour to amber when manual override is engaged.
FR-21-10 [ADDED v3.0] The system shall provide a Sensitivity Configuration panel allowing the user to adjust joystick sensitivity (expo curve) independently for each axis using a slider, with a preview graph showing the input-to-output curve.
FR-21-11 [ADDED v3.0] The system shall implement a dead-zone configuration for each joystick axis (0ΓÇô20% of travel), suppressing output below the dead-zone threshold to prevent unintended micro-commands.
FR-21-12 [ADDED v3.0] The system shall require the user to enable manual control explicitly via a two-step confirmation before the manual control input channels become active, preventing accidental activation.
FR-21-13 [ADDED v3.0] The system shall display a latency indicator on the Manual Control screen showing the round-trip command latency (ms) when connected to a live drone.

FR-25-07 [ADDED v3.0] The system shall provide an Airspace Data Last-Updated timestamp in the layer control, and display a stale data warning when airspace data is more than 24 hours old.
FR-25-08 [ADDED v3.0] The system shall cache the last-fetched airspace data locally so that previously viewed airspace boundaries remain visible when the device is offline, displayed with a visual indicator denoting that data may be outdated.
FR-25-09 [ADDED v3.0] The system shall display NOTAM markers on the map as pin icons when NOTAM data is available from the airspace provider, with a tap-to-expand panel showing the full NOTAM text.
3.26  Advanced Battery and Power Management UI [FR-26]
ADDED v3.0 ΓÇö Detailed power analytics, discharge prediction, and RTH battery planning.
FR-26-01 [ADDED v3.0] The system shall provide an Advanced Power panel within the telemetry section, accessible via a battery icon on the main dashboard.
FR-26-02 [ADDED v3.0] The system shall display a real-time battery discharge curve graph plotting cell voltage (V) against flight time (minutes), with a moving current-position marker.

FR-26-10 [ADDED v3.0] The system shall support configuration of up to 4 battery slots for multi-battery drone configurations, displaying independent voltage, current, and capacity data per slot.
3.27  System State Management [FR-27]
ADDED v3.0 ΓÇö Formal FSM definition with UI state indicators for all drone operational states.
FR-27-01 [ADDED v3.0] The system shall implement and enforce a drone operational Finite State Machine (FSM) with the following states: DISCONNECTED, CONNECTED_DISARMED, PRE_ARM_CHECK, ARMED_IDLE, TAKING_OFF, IN_MISSION, LOITERING, MANUAL_CONTROL, RETURNING_HOME, LANDING, LANDED, EMERGENCY.
FR-27-02 [ADDED v3.0] The system shall display the current FSM state prominently in the HUD status bar, using the state name and a distinct colour: DISCONNECTED (grey), CONNECTED_DISARMED (white), PRE_ARM_CHECK (amber), ARMED_IDLE (light green), TAKING_OFF (green), IN_MISSION (blue), LOITERING (cyan), MANUAL_CONTROL (yellow-green), RETURNING_HOME (orange), LANDING (orange-red), LANDED (green), EMERGENCY (red flashing).
FR-27-03 [ADDED v3.0] The system shall enforce the following valid state transitions, blocking any UI action that would result in an invalid transition: DISCONNECTED ΓåÆ CONNECTED_DISARMED (on connection); CONNECTED_DISARMED ΓåÆ PRE_ARM_CHECK (on arm command); PRE_ARM_CHECK ΓåÆ ARMED_IDLE (all checks pass) or CONNECTED_DISARMED (check failure/disarm); ARMED_IDLE ΓåÆ TAKING_OFF (on mission start or manual takeoff); TAKING_OFF ΓåÆ IN_MISSION or MANUAL_CONTROL; IN_MISSION Γåö LOITERING; IN_MISSION ΓåÆ RETURNING_HOME (on RTH command); RETURNING_HOME ΓåÆ LANDING; LANDING ΓåÆ LANDED; ANY_ARMED_STATE ΓåÆ EMERGENCY (on emergency stop); EMERGENCY ΓåÆ CONNECTED_DISARMED (on emergency clear and disarm).
FR-27-04 [ADDED v3.0] The system shall display a Pre-Arm Check panel during the PRE_ARM_CHECK state, listing each check item (sensor calibration, GPS lock, battery, RC signal, firmware version, geofence active) with individual pass/fail indicators and an aggregate result.
FR-27-05 [ADDED v3.0] The system shall disable mission start, takeoff, and arm controls when any mandatory pre-arm check is in a failed state, and display a tooltip identifying the failing check.
FR-27-06 [ADDED v3.0] The system shall display a state transition history log (last 20 transitions) accessible from the diagnostics panel, showing: previous state, new state, trigger event, and timestamp.
FR-27-07 [ADDED v3.0] The system shall provide a visual State Transition Diagram viewer (textual/graphic panel) in the Help section, displaying all valid states and transitions as a reference for operators.

4.1 Performance
NFR-01-01 The application shall launch and reach the main map screen within 3 seconds on a mid-range Android device (2 GB RAM, Snapdragon 665). [v2.0]
NFR-01-02 Map interactions (pan, zoom) shall maintain a minimum frame rate of 60 fps on supported devices. [v2.0]
NFR-01-03 Mission save and load operations shall complete within 500 milliseconds for missions containing up to 100 waypoints. [v2.0]
NFR-01-04 Simulation telemetry update rendering shall not cause visible jank (frame drops below 30 fps) on target devices. [v2.0]
NFR-01-05 Telemetry graph rendering shall update within 100 ms of receiving new data values. [v2.0]
NFR-01-06 PID response curve graph shall update within 200 ms of any slider or input change. [v2.0]
NFR-01-07 The survey grid auto-generation algorithm shall produce a complete waypoint set for a 100-hectare polygon within 2 seconds. [v2.0]
NFR-01-08 [ADDED v3.0] The manual control virtual joystick input shall be sampled and transmitted at a minimum of 20 Hz, and the UI channel value readouts shall update within 50 ms of a joystick position change.
NFR-01-09 [ADDED v3.0] The end-to-end latency from a manual joystick input event to the transmission of the corresponding MAVLink RC_CHANNELS_OVERRIDE message shall not exceed 100 ms on a Wi-Fi connection.
NFR-01-10 [ADDED v3.0] The camera live feed panel shall display frames with a maximum end-to-end latency of 500 ms from capture to display when connected via RTSP over a local Wi-Fi network.
NFR-01-11 [ADDED v3.0] The mission replay animation shall maintain smooth playback (minimum 30 fps interpolated position updates) for flight logs up to 6 hours in duration without pre-loading the entire log into memory.
NFR-01-12 [ADDED v3.0] Airspace polygon overlays shall render within 2 seconds of the map reaching a stable zoom level, and shall not block map interaction during loading.

8. Advanced Feature Specifications
8.1 Manual Control Input Pipeline
The manual control input pipeline processes joystick input through the following stages:
Raw Input Capture ΓÇö touch events or HID device events are captured at the platform layer at up to 120 Hz.
Dead-Zone Filtering ΓÇö inputs within the configured dead-zone threshold (FR-21-11) are clamped to zero.
Expo Curve Application ΓÇö remaining input is mapped through the configured exponential sensitivity curve (FR-21-10) to produce a normalised output value in the range [ΓêÆ1.0, +1.0] per axis.
Channel Mapping ΓÇö normalised axis values are mapped to PWM-equivalent channel values (1000ΓÇô2000 ┬╡s) per the configured joystick mode (FR-21-03).
Rate Limiting ΓÇö output values are rate-limited to prevent step changes > 200 ┬╡s/frame.
Command Emission ΓÇö channel values are emitted to the ManualControlController at 20 Hz, which packages them into MAVLink RC_CHANNELS_OVERRIDE messages for transmission.
8.2 Mission Replay Engine Architecture
The mission replay engine implements a streaming log reader to support replay of logs exceeding device RAM capacity. The engine maintains a 30-second sliding window of log samples in memory, pre-fetching ahead of the current playback position. Position interpolation uses linear interpolation between consecutive GPS samples. Timeline event detection uses a sorted event index built during log loading, enabling O(log n) scrubber seeks. Playback speed control adjusts the timer tick interval: at 1x speed, the timer fires every 250 ms (matching the 4 Hz log rate); at 10x, it fires every 25 ms, advancing the log cursor by 10 samples per tick.
8.3 Airspace Data Integration
The AirspaceDataService implements the following data lifecycle:
On map view stabilisation (after a 500 ms debounce following scroll/zoom), the service computes the current map bounding box and requests airspace data for that area from the configured provider API.
Received GeoJSON FeatureCollection is parsed and validated (NFR-04-08).
Valid zones are stored in the AirspaceRepository with a TTL of 24 hours.
Expired data is flagged with a stale indicator (FR-25-07) but retained for offline display.
The AirspaceController exposes a filtered stream of zones visible in the current viewport to the presentation layer, preventing off-screen polygon rendering.
8.4 Power Budget Model
The power consumption prediction model (FR-26-06) uses the following empirical formula:
P_total = (╬ú segment_distance_i / cruise_speed) ├ù I_avg ├ù V_nominal
Where: I_avg is the user-configured or historically measured average current draw (A), V_nominal is the configured battery nominal voltage (V), and segment_distance_i is the distance between consecutive waypoints. The model adds a hover penalty for each waypoint with hover_time > 0:
P_hover = hover_time ├ù I_hover ├ù V_nominal  (I_hover Γëê 0.6 ├ù I_avg by default)
RTH power estimate uses the direct distance from the final waypoint to Home point. All values are expressed in mAh and compared against the configured battery capacity (FR-13-11) to derive the feasibility indicator (FR-26-07).
8.5 FSM Implementation Notes
The FlightStateMachineNotifier implements the FSM as a Riverpod StateNotifier<FlightState>. State transitions are validated against a predefined transition table before being applied; invalid transitions throw an InvalidStateTransitionException which is caught by the Application layer and logged. The current state is persisted to SharedPreferences on every transition to survive application restarts. On app launch, if a persisted state is found that is incompatible with the current connection status (e.g., IN_MISSION but drone is disconnected), the FSM resets to DISCONNECTED with a user notification.
9. Future Scope
9.1 MAVLink Live Drone Integration
The MavlinkService stub defined in the Infrastructure Layer will be completed to parse and generate MAVLink v2 messages over UDP, TCP, or Serial connections. This will enable all simulated features ΓÇö telemetry, manual control, camera commands, firmware flashing, and FSM state ΓÇö to operate with real ArduPilot and PX4 autopilot hardware.
9.2 Cloud Mission Synchronisation
A CloudMissionRepository will be added to the Data Layer, backed by a REST API with JWT authentication. Missions, flight logs, and PID profiles will be synchronisable across multiple devices.
9.3 Advanced Multi-Vehicle Swarm Coordination
The multi-vehicle management UI (FR-29) will be extended with a swarm mission planner supporting coordinated waypoint assignment, formation flight patterns, and vehicle-to-vehicle conflict avoidance visualisation for up to 10 vehicles.
9.4 AI-Assisted Mission Planning and Anomaly Detection
An on-device ML inference module will provide: optimal waypoint recommendations based on terrain and objective type, real-time anomaly detection on telemetry streams (detecting unusual altitude excursions, battery voltage drops, vibration spikes), and automated post-flight analysis report generation.
9.5 Augmented Reality (AR) Overlay Mode
An AR camera view mode will overlay drone position, active waypoints, and telemetry HUD onto the device's live camera feed using device orientation sensors and GNSS for geo-registration.
9.6 Regulatory Compliance Reporting
The application will generate automated flight compliance reports summarising: airspace zones transited, maximum altitude reached, total flight time, and any regulatory threshold exceedances ΓÇö formatted for submission to relevant aviation authorities.

Actor | Remote Pilot (Manual) / Drone Operator
Preconditions | Application is in IN_MISSION state (autonomous flight active); drone is connected and armed.
Trigger | Operator taps the 'Manual Override' button on the mission execution HUD.
Main Flow | 1. System displays a confirmation dialog: 'Take manual control? Autonomous mission will be suspended.' 2. Operator confirms. 3. System transitions FSM to MANUAL_CONTROL state. 4. System displays 'MANUAL OVERRIDE ACTIVE' amber banner. 5. Virtual joystick becomes active; channel outputs reflect joystick position. 6. Operator manoeuvres drone manually. 7. Operator taps 'Return to Auto' button. 8. System transitions FSM back to IN_MISSION, resuming from the next waypoint.
Alternate Flow A | Operator cancels the confirmation dialog; autonomous mission continues uninterrupted.
Alternate Flow B | Operator connects a physical gamepad before tapping Manual Override; system detects the HID device and routes input from the physical controller instead of the on-screen joystick.
Alternate Flow C | Operator taps Emergency Stop during manual control; FSM transitions to EMERGENCY state; all channel outputs set to disarm values.
Postconditions | Drone is under manual control or autonomous control has been resumed; state is correctly reflected in the HUD.

Actor | Technician / Administrator
Preconditions | Administrator mode is active; firmware flash has been initiated (UC-08 Main Flow step 3).
Trigger | A checksum verification failure occurs during the VERIFYING phase of the firmware flash.
Main Flow | 1. System detects checksum mismatch between uploaded image and expected hash. 2. System transitions the firmware FSM to ERROR state. 3. System displays 'Flash Failed ΓÇö Verification Error' dialog with error code, expected hash (truncated), and actual hash (truncated). 4. System releases the navigation block, allowing the user to navigate. 5. System displays 'Retry' and 'Cancel' options. 6. Operator selects 'Retry'; system re-downloads the firmware image and re-initiates the flash sequence from the ERASING phase. 7. Second attempt succeeds; system displays success notification.
Alternate Flow A | Operator selects 'Cancel'; system resets the Firmware Management screen to IDLE state. A warning is displayed that the FC may be in an inconsistent state and recommends physical reset.
Alternate Flow B | Flash fails on the second retry; system displays a persistent error recommending manual recovery via USB DFU mode, and provides a link to the ArduPilot recovery documentation.
Postconditions | Flight controller firmware is either successfully updated or the failure is documented in the system log with error details; operator is informed of recovery steps.

Actor | Drone Operator / Remote Pilot
Preconditions | Drone is in any armed state (ARMED_IDLE, TAKING_OFF, IN_MISSION, LOITERING, MANUAL_CONTROL, RETURNING_HOME, LANDING).
Trigger | Operator presses and holds the Emergency Stop button for 1.5 seconds (long-press confirmation mechanism).
Main Flow | 1. After 1.5-second hold, system displays a 1-second countdown overlay: 'EMERGENCY STOP ΓÇö Release to cancel'. 2. Operator does not release; countdown completes. 3. System transitions FSM immediately to EMERGENCY state. 4. System sends MAVLink CMD_COMPONENT_ARM_DISARM with force-disarm flag. 5. System sets all channel outputs to disarm values. 6. HUD border flashes red; audio alert sounds. 7. System logs the emergency event with timestamp and previous state. 8. System displays 'EMERGENCY STOP ACTIVATED' persistent banner with 'Clear Emergency' button. 9. Operator taps 'Clear Emergency'; system transitions to CONNECTED_DISARMED after operator confirms all is safe.
Alternate Flow | Operator releases the button before the 1.5-second threshold; emergency stop is cancelled with no state change.
Postconditions | Drone motors disarmed; FSM in EMERGENCY or CONNECTED_DISARMED state; emergency event recorded in state transition log.
